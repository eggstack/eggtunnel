# Reverse Session M012 — 0.2.0 Release Qualification and Publication Gate

Status: blocked

Planning baseline: 0c8830e76d92c209485eaf955cbdb51bdc953413

Source roadmap:

- plans/subsystems/reverse-session-roadmap.md#post-01-maintenance-and-evolution

Applicable ADR:

- plans/adrs/ADR-0001-session-transport-and-egress-boundary.md

Primary class: capability / polish

Hard dependency: M011 strict closure.

Operational gate: tagging, crates.io publication, and GitHub release publication require explicit owner authorization.

## 1. Objective

Qualify the post-0.1 Eggtunnel line as the next public release, planned as `0.2.0`, with a coherent API/release narrative, exact-head package evidence, downstream registry-consumer evidence, and the existing four-target binary distribution contract.

M012 does not add tunnel capabilities. Its job is to freeze, version, package, verify, and—only after explicit authorization—publish the result.

## 2. Why 0.2.0

Since v0.1.0 the public library has gained material additive capability:

- configurable `RuntimePolicy`, `ResourceLimits`, and `TimeoutPolicy`;
- typed client/server builders and transport profiles;
- dynamic runtime Service registration;
- heartbeat health in Snapshot;
- structured tracing integration;
- subsequent client/runtime and sustained-qualification hardening from M010-M011.

For a pre-1.0 Rust crate, a minor release is the clearest signal for this expanded public surface. Do not republish these changes as a 0.1.x patch unless an explicit release-policy decision changes the plan before implementation.

## 3. Invariants

- M010/M011 implementation is frozen before release versioning begins.
- Wire protocol remains version 1.0 unless a separate accepted ADR/milestone changes it first.
- Existing v0.1.0 release artifacts/history are immutable.
- The supported binary target set is evidence-based.
- The CLI remains `publish = false` unless separately authorized.
- Crates publication order remains `eggtunnel-proto` then `eggtunnel`.
- No crate publication, tag, or GitHub release occurs without explicit owner authorization.
- Release packaging does not introduce a new updater.
- Checksums are integrity evidence, not independent authenticity proof.

## 4. Planning-time shared-infrastructure decision

At the M012 planning baseline, Eggpack has closed its manifest builder, ReleasePlan interface, direct bootstrap installer generator, and Eggup interface fixture, but:

- CI Orchestration M001 is only ready to be planned;
- ecosystem adoption remains blocked on the remaining generator/CI capabilities.

Therefore Eggtunnel's existing release workflow remains authoritative for this release plan.

At M012 execution start, re-inspect Eggpack. If a stable, adopted producer interface now exists, do not silently rewrite Eggtunnel's release machinery inside the release candidate. Register a separate Eggpack-adoption migration unless the interface has already been explicitly approved for Eggtunnel and can preserve all M006/M012 evidence without scope growth.

## 5. Version and package changes

Update the workspace release version to `0.2.0` and reconcile every version-coupled location, including:

- root workspace package version;
- `eggtunnel` dependency requirement on `eggtunnel-proto`;
- package/readme examples that name the current crate version;
- distribution/current-release documentation only at the appropriate candidate/published stage;
- installer/release tests that consume tag/version metadata;
- downstream fixture expectations where they intentionally pin a published version.

Do not change protocol version merely because crate version changes.

## 6. Public API and semver review

Review the public surface against published 0.1.0.

At minimum:

- `Client`, `ClientHandle`, `ClientBuilder`, `ClientConfig`;
- `Server`, `ServerHandle`, `ServerBuilder`, `ServerConfig`;
- transport profile enums;
- runtime policy types;
- Service/Target connector types;
- Snapshot/heartbeat/termination/error types;
- proto public DTOs/constants.

Run a public-API/semver comparison tool such as `cargo-semver-checks` if practical. Treat it as evidence and review, not as a substitute for understanding 0.x compatibility. Any unexpected removal or signature break must be either fixed or explicitly documented as an intentional 0.2 break before publication.

## 7. Release documentation

Add/update a concise release narrative covering changes since v0.1.0.

A `CHANGELOG.md` MAY be introduced if the repository still lacks one; otherwise use the existing release-document convention.

Documentation must accurately cover:

- builders/runtime policy;
- dynamic Service registration semantics and one-in-flight limitation;
- heartbeat Snapshot fields;
- tracing behavior/no subscriber installation;
- supported transports and rejected combinations;
- four supported binary targets;
- no self-update engine;
- protocol remains wire 1.0;
- current known dependency warning, if still present.

Do not claim Eggbench/Eggchaos performance/security numbers as product guarantees.

## 8. Release target matrix

Preserve the M006 supported target set unless M012 adds equivalent full evidence for a new target:

- `x86_64-unknown-linux-gnu`;
- `aarch64-unknown-linux-gnu`;
- `x86_64-apple-darwin`;
- `aarch64-apple-darwin`.

Windows, musl, armv7, Raspberry Pi, and Le Potato remain unsupported unless the implementation produces release artifact, install, and runtime evidence sufficient to update the support contract.

Do not broaden the target matrix from compile-only evidence.

## 9. Package and downstream qualification

Before publication:

- `cargo package -p eggtunnel-proto` and inspect contents;
- `cargo package -p eggtunnel` and inspect contents;
- verify generated package metadata/readmes/docs;
- test the downstream embedder against the 0.2 candidate package where practical;
- after authorized crate publication, create a clean temporary consumer that resolves `eggtunnel = "0.2"` from crates.io with `default-features = false`, `client,tls`, and compiles/runs a public-API smoke without path patches.

The registry-consumer evidence is required before final publication closure.

## 10. Supply-chain and provenance

On the exact candidate:

- locked full CI;
- Rust 1.89 lane;
- all seven supported feature slices;
- minimal-dependency guard;
- `cargo audit`;
- `cargo deny check licenses`;
- generated third-party notices;
- release archive contents;
- SHA-256 manifest;
- GitHub artifact attestations through the existing workflow;
- install/version smoke for all four supported archives.

The transitive `atomic-polyfill` warning may remain informational if it is still target-gated, unmaintained-only, and not a known vulnerability; re-evaluate rather than copying the old conclusion.

## 11. Release workflow and authorization sequence

The implementation agent may prepare the exact release candidate and all pre-publication evidence.

Before any irreversible action, stop for explicit owner authorization.

After authorization, the expected order is:

1. finalize exact release commit;
2. create/push `v0.2.0` tag matching workspace version;
3. require the tag-triggered GitHub Release workflow to pass all four target builds/install smokes and publish release assets;
4. publish `eggtunnel-proto 0.2.0` to crates.io;
5. publish `eggtunnel 0.2.0` after the proto dependency is resolvable;
6. run the clean registry-consumer qualification;
7. update current-release documentation/closure evidence if publication creates new URLs/identifiers;
8. rerun ordinary CI for any post-publication documentation-only closure commit.

If authorization is not granted, leave M012 at an accurate candidate/operational-gate status; do not mark publication complete.

## 12. Performance/robustness carry-forward

M011 evidence is release-supporting but not a promise of fixed throughput.

Release notes may state that sustained fuzz/soak/performance qualification was added, with a link to repository evidence. Do not convert host-specific benchmark values into universal performance claims.

Any M011 high/medium unresolved finding blocks M012.

## 13. Required broad verification

Before the publication gate:

```sh
cargo fmt --all -- --check
cargo check --locked --workspace --all-targets
cargo test --locked --workspace --all-targets --all-features
cargo clippy --locked --workspace --all-targets --all-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --locked --workspace --all-features --no-deps
cargo check --locked --manifest-path fixtures/embedder/Cargo.toml
cargo audit
cargo deny check licenses
```

Also require:

- seven feature slices;
- Rust 1.89 checks;
- minimal dependency guard;
- M011 sustained qualification smoke/regression commands;
- package inspection;
- semver/API comparison;
- installer tests.

After tag/publication, require the hosted release run and clean registry consumer.

## 14. Acceptance criteria

M012 is complete only when:

- M010 and M011 are strictly closed;
- version/package references consistently describe 0.2.0;
- public API changes from 0.1.0 are reviewed and documented;
- protocol remains truthfully documented as wire 1.0;
- package contents are correct;
- all normal, feature, MSRV, security/license, sustained-qualification, and installer gates pass;
- the four-target release workflow passes on the exact authorized tag;
- if publication is authorized, proto then library publication succeeds and a clean `eggtunnel = "0.2"` consumer qualifies;
- current-release documentation matches actual publication state;
- no unresolved high/medium finding remains.

If publication is intentionally withheld, disposition must explicitly distinguish “release candidate qualified” from “0.2.0 published.”

## 15. Stop conditions

Stop and report if:

- a public API break is discovered but not intentionally documented;
- package versioning would accidentally alter protocol compatibility meaning;
- a supported target fails release/install evidence;
- Eggpack migration would materially expand the release candidate;
- crates.io publication order cannot resolve cleanly;
- audit/license findings become a known vulnerability or policy violation;
- release artifact contents differ across the intended build path.
